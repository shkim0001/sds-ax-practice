Day 4: 자산 조회 도구는 장애를 어떻게 견디나?

Long image

A

Answer

get_asset_status는 예외를 던지지 않습니다. 실패를 세 종류로 갈라 백엔드를 최대 3번까지만 부르고, 그래도 안 되면 get_asset_status_backup 캐시 값으로 답합니다.

  1. 타임아웃은 다시 물으면 답이 달라질 수 있어서 짧게 재시도합니다.1
  2. 스키마 오류나 없는 자원은 몇 번을 물어도 같아서 1번 만에 대체 경로로 넘어갑니다.
  3. 대체 경로로 답할 때는 반환 문자열에 get_asset_status_backup 이름과 실패 분류를 남깁니다.
  4. 반환값과 로그에 나가는 모든 문자열은 _redact를 거쳐 토큰이 지워집니다.2

호출 한 번은 어떤 길을 지나나?

Diagram structure
  • get_asset_status call
  • 정상 응답 ok
  • asset_id 검증 validate
  • fetch(asset_id) fetch
  • _format_asset format
  • classify_failure classify
  • 대기 후 재시도 wait
  • get_asset_status_backup backup
  • 폴백 안내 문자열 fbreply
  • backup → fbreply · 캐시 값
  • call → validate · 호출
  • wait → backup · 상한 도달
  • classify → backup · fatal: 즉시
  • format → ok · 반환
  • fetch → classify · 예외
  • wait → fetch · 재시도
  • fetch → format · 성공
  • classify → wait · retryable · backoff
  • validate → fetch · 유효 ID
  1. asset_id 검증 ↗

    빈 ID면 백엔드를 부르지 않고 등록된 ID 목록을 안내합니다.

  2. fetch(asset_id) ↗

    외부 백엔드를 부릅니다. 첫 시도와 재시도를 합쳐 3번을 넘지 않습니다.

  3. classify_failure ↗

    예외 타입과 메시지로 retryable, backoff, fatal 중 하나를 고릅니다.

  4. 대기 후 재시도 ↗

    retryable은 0.05초, backoff는 0.2초 다음 0.4초를 쉬고 다시 부릅니다.

  5. get_asset_status_backup ↗

    fatal이거나 3번을 다 쓰면 캐시에서 값을 꺼냅니다.

  6. 폴백 안내 문자열 ↗

    경로 이름, 분류, 호출 횟수, 캐시라는 경고를 함께 돌려줍니다.

  7. 정상 응답 ↗

    재시도 끝에 성공하면 되살아난 응답을 그대로 씁니다.

2

실패 종류마다 무엇이 달라지나?

분류판정 근거대응백엔드 호출
retryableTimeoutError, ConnectionError, 판정이 안 되는 오류0.05초 쉬고 재시도채점 2~3번3번
backoff메시지에 429, rate limit, too many requests0.2초, 0.4초로 간격을 늘려 재시도3번
fatalLookupError, ValueError, 권한·스키마·not found재시도 없이 즉시 대체 경로채점 1번 이하1번

판정 순서

backoff 키워드를 가장 먼저 봅니다. 429 메시지를 담은 RuntimeError가 retryable로 새지 않게 하려는 순서입니다. 그다음 예외 타입으로 fatal과 retryable을 가르고, 타입으로 모르면 메시지 키워드를 봅니다.
